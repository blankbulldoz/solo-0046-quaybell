# R-049 积压现场复原与取证

## 结论

值班看到的“有积压、两个客户端一取就空”，在本库里可以由两处互不相同、但在看板队列样本里完全一样的现场解释：

| 现场 | 消费组 | 目标队头（顺序键 `target-lane`） | 目标后继 |
| --- | --- | --- | --- |
| A | **仍暂停**（`paused=true`） | 投递 #21 仍是 `leased`，第 1 次尝试 `open`，租约截止 1730000004 已过但**未回收** | 投递 #22 被 #21 挡住，`waiting` |
| B | **已恢复**（`paused=false`） | 投递 #21 已是 `waiting`，第 1 次尝试 `expired`、回收于 1730000005，**就绪时刻 1730000007** | 投递 #22 被 #21 挡住，`waiting` |

两处的看板队列样本都是同二十行（`#1`–`#20`，填充车道），**目标投递 #21/#22 根本不在样本里**，所以“看板一样、领取为空”成立。区别只在完整响应的两处：

* 分类计数：A 是 `expired=1`，B 是 `delayed=1`（都是 10 个 `leased`、11 个 `blocked`）；
* 目标队头的尝试结果：A 是 `open`（租约在手、已过期未回收），B 是 `expired`（已回收、正在退避）。

后继 #22 在两处的轨迹完全相同（`waiting`、零尝试、`ready_at=1730000000`），所以**单看后继无法区分**，也不能把空领取归因于后继。

看板的“近期消息”表按消息号倒序列出最近 30 条，A/B 里都能看到 `target-head` 和 `target-next`，因此可以**从看板本身定位到消息号**，再去读 `GET /v1/messages/{id}`。这一点很关键：不用领取也能把目标从二十行样本之外找回来。

## 现场该看什么（非干预证据）

按以下顺序只用读接口，不领取、不暂停、不回收、不确认：

1. `GET /v1/channels/{channel}`：看板。先核对 `groups[].paused` 和完整 `counts`，再从 `messages` 表里按生产键/顺序键定位疑似目标的消息号；样本没有目标时，这一步就是“非干预地找回目标”的入口。
2. `GET /v1/messages/{id}`：目标队头与后继的投递、尝试和事件。队头事件里出现 `expired` 一条，说明已回收并转入退避；只有 `published`+`leased` 且尝试为 `open`，说明过期未回收。
3. `GET /v1/messages/{id}/evidence`：下载 `quaybell-trace/1`，按内容重算 `sha256`。导出不含租约凭据，可作为交接附件。

`python3 -m examples.triage` 会先复制一份只读副本，在副本上做上述 GET，并在读取前后各算一次行级摘要、对原库文件做字节摘要：`read_only.unchanged=true` 且 `source_unchanged_bytewise=true` 表示这套只读读法没有改动任何数据。行级摘要把 `token_digest` 排除在外，因此摘要只反映业务行，不暴露凭据。

## 副本里验证“解除暂停 / 等待是否足够”

原始库不动；每次实验先把 `scene-*.sqlite3` 复制一份，再在副本上操作。结论全部记录为布尔值，`--verify` 会重跑并逐项比对。

* `a-paused-wait-only`：仍暂停只等待，两个客户端依次领取都为空；到推导出的就绪时刻 1730000007 仍为空，再等到 +300 秒也仍为空。**A 只等待不够。**
* `a-unpause-at-observe`：在 1730000005 解除暂停后立刻领取，仍为空；这一领把队头从“过期未回收”变成“已回收、退避到 1730000007”，**领取有副作用**。到 1730000007 再领才拿到 #21（第 2 次尝试），确认后 #22 可领。
* `a-unpause-at-ready`：等到 1730000007 再解除暂停，一次领取就完成回收并拿到 #21，不需要另行回收。确认后 #22 可领。
* `a-sweep-while-paused`：暂停中先全局回收，队头转为 `waiting`、就绪 1730000007，但暂停仍挡住领取，到点领取仍为空。**回收不能绕过暂停。**
* `b-wait-only`：已恢复，两个客户端依次领取都为空且不改库；无需暂停或回收，到 1730000007 领取拿到 #21，确认后 #22 可领。**B 只等待足够。**

因此：A 需要先解除暂停，并且从观察时刻起至少要再等一个退避周期（到 1730000007）；B 什么都不用做，等到 1730000007 即可。两条路都会在退避结束后先投递 #21，再由确认解开 #22。

## 取证材料

仓库内 `docs/r049/`：

* `bundle.json`：完整取证包（`quaybell-r049-triage/1`），含两处场景的看板、轨迹、证据导出原文、行级摘要、五个副本实验的逐步记录和结论、只读校验结果、样本局限和“只有样本时须保留的结论”。文件内含自校验 `sha256`。
* `scene-a-head.evidence.json`、`scene-a-successor.evidence.json`、`scene-b-head.evidence.json`、`scene-b-successor.evidence.json`：四份 `quaybell-trace/1` 导出原文（已去凭据）。

复跑：

```sh
python3 -m compileall -q quaybell examples
python3 -m examples.triage                    # 重建并打印摘要，任一结论不为真即失败
python3 -m examples.triage --verify docs/r049 # 重建两个现场并与已存取证包逐项比对
python3 -m examples.triage --export /tmp/r049 # 重新导出一份取证包
```

`--verify` 会校验已存 `bundle.json` 的 `sha256`、重建结果与它完全一致、四份证据导出重新计算摘要通过且与包内原文逐字节相同。整个复原使用受控时钟和本机回环实例，同一代码三次导出的摘要相同。

## 如果接班人只拿到看板样本

样本只有二十行、且不含目标投递时，以下结论**必须保留**（取证包 `sample_only_caveats` 有同样的清单）：

1. 不能断定目标“藏在某条被阻挡的后继里”还是“根本不存在”，也不能断定它属于哪条顺序键。
2. 样本里看不到尝试结果，**不能区分 A（租约过期未回收）和 B（已回收正在退避）**——两处样本完全相同。
3. 样本里看不到 `ready_at` 和尝试次数，因此算不出还要等多久，也不能断言“再等一次就够”。
4. 样本只给暂停标志，**不能证明暂停是空领取的唯一原因**：A 解除暂停后仍要再等一个退避周期。
5. 样本没有完整计数的明细，不能排除其他顺序键上的独立阻挡或迟延。
6. 仅凭样本无法判断补齐证据要用哪几个读接口，更不能据此决定回收或重投。

## 本次未覆盖

* 领取本身会先回收本组最多 100 条到期尝试（`claims` 先 `expiry.reap`），所以“领取”不是中性观测；现场不要用它试探。
* `max_attempts=2`：目标第 2 次尝试若再失败会进死信，本取证到确认 #21 为止，未覆盖死信分支。
* 受控时钟、单实例回环；真实时钟偏差、并发领取、跨组回收竞争都不在覆盖内。
* 样本上限来自 `quaybell/overview.py` 的 `len(sample) < 20`，计数覆盖全部投递，两者口径不同。

# 0001 热键隔离、消费组拆分与顺序键固定归属

- 状态：决策建议，待评审
- 日期：2026-11-27
- 基线提交：`08573d3`
- 范围：Quaybell 同一消费组内持续热键、大量低频顺序键、消费者归属切换、租约/重试、上线并发证明与旧积压收尾

## 1. 建议结论

采用“**先确认 `lane` 粒度和延迟层级，再做热点隔离；长尾键留在同组内按键串行执行**”的混合方案，而不是无条件拆组，也不要把未经 Broker 支持的“同组进程固定归属”当作强互斥机制。

1. **Quaybell 的顺序键是 `lane`，不是生产键 `key`。** 同一消费组内，一个 `lane` 的最早未处置投递会挡住该 `lane` 的后继；不同 `lane` 在 Broker 层本来就可以并行领取。见 `quaybell/eligibility.py:5`。
2. **“拆多个消费组”不等于拆分同一队列的消费者。** Quaybell 消费组是扇出订阅：每条匹配消息会给每个匹配组各创建一条投递。用相同筛选条件建多个组会得到多份独立消息，不是竞争分区。见 `quaybell/publication.py:36`。
3. **持续热键且需要独立资源、暂停、死信或容量隔离时**，由生产者增加路由标签，建互斥标签的热键组和低频组，使用独立工作池。若热键要求严格顺序，该 `lane` 在该组内仍只能保持一个有效处理者；增加同组消费者不能提高单键安全并行度。
4. **一批低频键应留在同一个组**，多个消费者并行领取不同 `lane`，进程内用 `lane -> actor/队列` 保证同键串行。可以做一致性哈希亲和以提高缓存命中，但这只能称为“亲和”，不能默认为强“归属”。
5. **当前领取接口没有 `lane`、键范围或属主过滤参数，也没有主动释放/转让租约或续租接口。** `worker` 只是记录在尝试上的审计名称，不执行归属鉴权。见 `quaybell/claims.py:6`、`quaybell/attempts.py:10`。因此跨进程固定归属若要求正确性，必须额外实现属主协调与栅栏，或用标签分片组把归属边界变成 Broker 路由边界；否则应先补 Broker 的键过滤领取/租约转让能力。
6. **在手有效租约期间不能立即把同一投递安全切换给新属主。** 新属主会查不到该 `lane` 的当前投递和后继。优雅路径是旧属主在租约内完成并 `ack`，或主动 `nack`；异常路径只能等租约到期、回收和退避结束后产生新尝试、新令牌。
7. **租约到期只使旧令牌不能再向 Quaybell 提交结果，并不会杀死旧进程。** 因此上线前必须证明两件事：Broker 不会发出两个同时有效的同键尝试；僵尸旧属主即使继续访问业务系统，其旧栅栏写入也会被拒绝或被幂等键去重。只看工作进程日志里的“没有同时进入处理函数”不足以覆盖暂停、GC、网络分区和超时重试。
8. **旧积压由原消费组的服务负责人/当班 DRI 收尾。** 新建消费组只接收建组后匹配的新发布，不会追认旧消息，也没有把等待中投递移动到另一个组的接口。同组归属调整时，旧属主负责在手尝试，最终键属主负责剩余积压，值班负责人负责死信和重投。

## 2. 现行投递与确认语义

以下事实是决策边界：

- 领取在一个 `BEGIN IMMEDIATE` 写事务中完成；SQLite 写事务串行化，资格查询和租约写入之间没有并发提交缺口。见 `quaybell/persistence.py:30`、`quaybell/claims.py:13`。
- 合格投递必须是 `waiting` 且 `ready_at <= now`，并且同一 `subscription_id + lane + id` 更早的投递不能处于 `waiting` 或 `leased`。见 `quaybell/eligibility.py:5`。
- 每次领取最多 30 条，按投递 ID 排序；每次领取会先在本组回收最多 100 个已到期尝试。见 `quaybell/claims.py:7`、`quaybell/claims.py:11`。
- 领取后投递变 `leased`，生成新的尝试编号和随机令牌；数据库部分唯一索引保证一个投递至多一个 `open` 尝试。见 `quaybell/schema.py:78`。
- 相同令牌、相同结果和原因的重复确认/拒绝会返回已记录回执及 `repeated: true`。其他情况下，只要尝试不是 `open`、投递不是 `leased`，或 `expires <= now`，就返回 409。见 `quaybell/disposition.py:14`。
- 明确 `nack` 的退避从处置时间起算；租约超时的退避从原租约截止时间起算。首次重试延迟为 `retry_seconds`，之后指数增长，上限 3600 秒。见 `quaybell/outcomes.py:12`、`quaybell/policy.py:38`。
- 领取本身会触发本组有界回收，全局 `POST /v1/sweep` 也可回收；没有常驻回收线程。暂停组的领取会在回收前直接返回 `paused`，因此暂停组的到期租约需要 `/sweep` 或其他回收触发。
- 投递绑定发布时的策略版本；该投递的后续尝试仍使用原策略。只有死信重投追加的新投递使用当前策略。见 `quaybell/outcomes.py:8`、`quaybell/redrive.py:9`。
- 尝试次数用尽后投递变 `dead`。死信是终态，不再阻挡同 `lane` 后继。重投会在**同组、同 `lane` 的队尾**追加一个后继投递；同一死信源至多有一个直接后继。见 `quaybell/outcomes.py:9`、`quaybell/redrive.py:10`。
- 订阅标签是全部键值精确匹配，没有 `lane` 订阅过滤，也没有“非某标签”规则。见 `quaybell/routing.py:5`。

### 先判断热键是否真的在 Broker 层延后冷键

查看 `GET /v1/channels/{channel}` 的同快照分组样本。每个未处置投递会被归为一种原因：

- `blocked`：被同一 `lane` 的更早未处置投递挡住；样本中的 `head_id` 是该 `lane` 队首。
- `ready`：Broker 已可领取，但没有消费者及时领走，通常是消费并发、轮询、批量串行处理或容量问题。
- `leased`：已有有效在手租约，处理变慢或工作进程卡住。
- `expired`：租约已到截止时间，但可能尚未被回收。
- `delayed`：计划延迟或失败退避尚未结束。
- `paused`：组被暂停。

如果冷键和热键的 `lane` 不同，冷键出现持续 `blocked` 通常说明：

1. 业务上把多个实体错误映射成了同一个粗粒度 `lane`；或
2. 观察的是消费者本地串行队列，而不是 Quaybell 的领取资格。

若冷键是 `ready` 但年龄增长，拆 Broker 顺序键规则不会直接解决问题；需要提高处理并发、避免一个批量内串行等待，或隔离资源池。

## 3. 两个典型例子

### 3.1 持续热键：`lane=ledger-88`

假设同一组中有：

- `H1、H2……Hn`：全部使用 `lane=ledger-88`，持续高速产生；
- `C1`：`lane=batch-a`；
- `C2`：`lane=batch-b`。

用 `lease_seconds=10`、`retry_seconds=5` 的受控时钟实际推演，发布顺序为 `H1,H2,C1,C2`：

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| T=0 | 属主 A 以 `limit=1` 领取 | 得到投递 1，即 `H1/ledger-88`，尝试 1，租约 T=10 到期 |
| T=0 | B 领取 2 条 | 得到投递 3、4，即 `C1/batch-a`、`C2/batch-b` |
| T=0 | B 在 A 租约有效期内再领取 | 返回空；`H2` 仍被 `H1` 挡住 |
| T=10 | A 用旧令牌首次 `ack` | 409：`租约已处置或超时`；此刻尚未回收，状态仍可能显示 `leased/expired` |
| T=10 | B 发起领取 | 先回收 `H1` 尝试 1；超时重试从原截止 T=10 起算 5 秒，因此本次领不到 `H1` |
| T=15 | B 再领取 | 得到投递 1 的尝试 2 和新令牌；A 的旧令牌再确认仍为 409 |
| T=15+ | B `ack` 尝试 2，再领取 | `H1` 终态后，才得到 `H2`，且 `H2` 是自己的尝试 1 |

这说明热键的在手投递只会挡住**同一 `lane` 的后继**；`batch-a`、`batch-b` 在 Broker 层没有被挡住。团队看到的“冷键延后”若发生在工作进程内，常见原因是：

- 所有进程一次 `claim(limit=30)` 后按返回顺序串行处理，热键队首排在批内前面；
- 部署容量按单串行消费者设计，热键占满工作线程/连接池/下游配额；
- 所有消息误用了同一个 `lane`；
- 一致性哈希把热键和一批冷键分给同一个实例，而该实例的事件循环/线程池被热键阻塞。

#### 何时为持续热键拆组

满足以下任一项时，建议拆成标签路由的专用组：

- 热键的处理耗时或重试会长期占满一个关键工作池，冷键 SLO 受影响；
- 热键需要独立扩容、限流、暂停、告警、死信值班或发布节奏；
- 热键数量少且身份稳定，可以由生产者可靠地加上 `traffic=hot`、`hot_shard=<n>` 等标签；
- 需要把热键的积压和死信放在独立看板/值班流程中。

推荐拓扑：

```text
channel=orders
  group=hot-ledger-88   tags={"traffic":"hot","hot_id":"ledger-88"}
  group=batch           tags={"traffic":"batch"}
```

发布前用 `/v1/channels/orders/preview` 验证标签匹配。注意标签规则没有“不等于”，因此热、冷消息都应由生产者显式打标；未打标消息不会进入带标签组。

如果热键大到一个工作进程仍处理不过来，**不能靠多个消费者同时领取同一 `lane` 来水平扩展**，因为这会破坏当前顺序边界。可选办法是：

- 缩短单条处理时间、批量聚合或合并提交；
- 把一个大热实体拆成不会违反业务顺序的子键；
- 在业务允许时改为快照 + 增量，而不是让每条事件都串行访问同一热点行。

如果热键和冷键需要不同的 `lease_seconds`、`retry_seconds`、`max_attempts` 或保留期，同频道组仍共享频道策略；这时应拆到独立频道，而不是只拆组。

### 3.2 一批低频键：`lane=acct-0001...acct-N`

这批键每个键每分钟甚至每天只有少量消息，但键数量很多，顺序只在单个账户/设备/单据内有意义。

建议：

1. 保留一个标签组，例如 `batch`。
2. 部署多个无固定键状态的竞争消费者。
3. 每个消费者维护有界的 `lane -> 串行 actor/队列`：
   - 领到消息后按 `lane` 投递到对应 actor；
   - 同一 `lane` 前一条未完成业务处理和提交前，不并发执行下一条；
   - 不同 `lane` 立即并行。
4. `claim limit` 与本地 actor 容量匹配，避免一次领取过多，导致消息在本地队列中超过租约。当前没有续租接口，租约应大于“排队 + 处理 + 下游超时”的高分位总时长，并预留时钟和重试余量。
5. 可用确定性哈希把同一 `lane` 优先路由到某个本地缓存属主，但应把它实现为**可丢失、可重建的缓存亲和**：
   - 缓存未命中时任何消费者都能安全处理；
   - 属主变化不需要搬迁锁或承认旧属主的未提交写入；
   - 真正的互斥由 Quaybell 租约、业务幂等和栅栏保证。

#### 何时需要把低频键也固定到跨进程属主

如果处理逻辑依赖进程内独占状态、本地写缓存、设备会话或不可重入资源，普通“竞争领取 + 缓存亲和”不够。此时有两个现行版本可落地的选择：

- **静态/虚拟分片标签组**：生产者计算 `shard=hash(lane)%32`，建立 `batch-s00` 到 `batch-s31` 组，每组由固定部署集合消费。某个实例故障时，其分片组由备用实例接管。这是把固定归属下沉为 Quaybell 可匹配的标签边界。
- **增强 Quaybell**：增加按 `lane`/分片过滤领取、服务端属主租约、心跳续租和安全释放/转让。没有这些原语前，不要只靠所有工作进程自觉执行哈希，因为非属主仍可能通过普通 `claim` 领到该 `lane`；若它处理，破坏归属，若它随意 `nack` 或等租约过期，又会消耗尝试预算并增加延迟。

不建议为每个低频键建一个组：组数量和运维看板会变成新的热点，且大多数组长期为空。应按少量稳定虚拟分片聚合。

## 4. 在手租约与重试时如何切换属主

不存在“立即接管有效租约”的接口。暂停组也不会使已有令牌失效。切换只能沿状态机发生。

### 4.1 优雅切换

旧属主 A 收到下线/重平衡信号后：

1. 停止领取新消息，尤其停止领取新的 `lane`。
2. 对已领取消息停止接受新的外部副作用步骤。
3. 在租约截止前完成并使用原令牌 `ack`；确认响应丢失时，用同一请求/令牌重试，会得到同一回执和 `repeated: true`。
4. 如果无法在租约内安全完成，应在到期前主动 `nack`，并记录原因。投递回到 `waiting`，就绪时间为 `nack` 处置时间加当前尝试对应的退避。
5. `ack` 提交后，新属主下一次领取即可得到该 `lane` 的后继；`nack` 后则需等待 `ready_at`。

这是唯一能把切换延迟控制在预期内且不产生过期僵尸窗口的方式。

### 4.2 崩溃、卡顿或错过租约

1. A 的尝试 1 令牌在 `expires` 时刻失效。若此前没有成功记录同结果应答，A 在 `expires <= now` 后确认会得到 409。
2. 到期记录不会由工作进程本地时钟自动改变；下一次本组 `claim` 的回收步骤或全局 `/sweep` 会把尝试记为 `expired`，并把投递置回 `waiting`。
3. 超时重试的 `ready_at = 原 expires + retry_seconds * 2^(attempt-1)`，上限 3600 秒。若回收发生得晚且 `ready_at` 已过，回收后的同一次/下一次领取可能立刻产生尝试 2。
4. 新属主 B 拿到的是新尝试编号和新令牌。A 的旧令牌之后无论 `ack` 还是 `nack` 都只能得到 409。
5. 如果每次尝试都失败/超时并达到 `max_attempts`，投递进入 `dead`，后续热键消息解除阻挡。死信问题修复后，重投子投递会排到同 `lane` 当前队尾，而不是插到最前。

默认策略下，第一次租约 24 秒、首次退避 3 秒；若旧属主完全无响应且新消费者持续轮询，常见接管下限约为租约剩余时间 + 3 秒，另加轮询和有界回收延迟。若已经是第 `n` 次尝试，退避为 `3 * 2^(n-1)` 秒。

### 4.3 为什么还需要栅栏和幂等

Quaybell 能保证不会有两个已提交的、当前有效的 Broker 租约，但不能保证旧进程在租约到期后已经停止运行。例如：

- 进程发生长 GC 或调度停顿；
- 到下游数据库的请求卡住，恢复后继续提交；
- 主机被 `SIGSTOP`/挂起后恢复；
- 网络分区中旧属主认为自己仍持有租约。

因此端到端正确性不能表述为“任何时刻两个进程的处理函数绝不重叠”，而应表述为：

> 同一 `(channel, group, lane/delivery)` 的任意两个尝试代际中，只有最新代际能够提交有效业务结果；旧代际的延迟提交必须被栅栏拒绝，或被业务幂等键去重。

建议：

- 以 `(delivery_id, attempts.number)` 作为单调栅栏；同一 `lane` 上 `delivery_id` 单调递增，重投子投递也有新的 `delivery_id`。
- 下游提交使用条件更新或栅栏表，拒绝较旧的 `(delivery_id, attempt)`。
- 普通重试使用 `(channel, consumer_group, message_id)` 作为稳定业务幂等键；不要每次尝试都更换幂等键。
- 对死信重投要显式决定业务语义：如果修复后必须重新执行业务副作用，可把重投子投递 ID 纳入处理身份；如果重投同一消息只是为了补齐同一业务结果，则继续使用消息/组幂等键。README 已明确提示这一区别。
- 处理过程中检查租约截止时间，超过安全点后不再发起新的非幂等外部操作；但截止时间检查只能降低风险，不能替代栅栏。

## 5. 上线前如何证明同键没有并行处理

当前仓库说明正式测试套件仍延后建设，因此不能只依赖手工演示。建议把以下检查作为上线门禁，并保留一次干净环境中的运行记录。

### 5.1 先跑现有有界工作流

在仓库根目录执行：

```sh
python3 -m compileall -q quaybell examples

for w in channel revision group preview publish claim ack retry sweep \
         dead redrive board retention export; do
  python3 -m examples.walkthrough "$w"
done
```

这些工作流覆盖同键队首、异键并行、幂等确认、退避、过期回收、死信重投和看板原因。本建议撰写时，上述 15 个工作流均已跑通。

### 5.2 必须新增的并发与故障注入测试

至少覆盖以下场景，并且测试要启动真实 HTTP/SQLite 实例，而不是只 mock 资格函数：

1. **并发领取不变量**
   - 发布 1 个持续热 `lane` 的 100 条消息和 100 个不同低频 `lane`。
   - 启动至少 8 个工作线程/进程并发 `claim(limit=1..30)`、随机短处理并 `ack`。
   - 在测试进程内维护每个 `lane` 的活跃处理计数，断言最大值始终为 1。
   - 断言每个投递不会在未终态时被重复领取，批量响应中同一 `lane` 至多出现一次。

2. **数据库不变量**

   测试结束后或运行中反复检查：

   ```sql
   -- 每个投递至多一个开放尝试；部分唯一索引也会强制这一点
   SELECT delivery_id, COUNT(*) AS n
   FROM attempts
   WHERE outcome = 'open'
   GROUP BY delivery_id
   HAVING n > 1;

   -- 同一消费组 + 顺序键至多一个 leased 投递
   SELECT subscription_id, lane, COUNT(*) AS n
   FROM deliveries
   WHERE state = 'leased'
   GROUP BY subscription_id, lane
   HAVING n > 1;
   ```

   两个查询都必须返回 0 行。还应断言所有发布投递最终 `acked`，或按测试设计进入 `dead`/重投终态。

3. **确认响应丢失重试**
   - 同一令牌并发或重复发送相同 `ack`。
   - 断言全部得到兼容回执，且响应中的 `repeated` 符合首次/重试事实。
   - 断言业务副作用只生效一次。

4. **`nack` 代际切换**
   - 第一次尝试 `nack` 后，在 `ready_at` 前领取必须为空。
   - 到 `ready_at` 后得到尝试 2 和新令牌。
   - 旧令牌的 `ack/nack` 均为 409。
   - 校验退避时间等于处置时间加 `retry_seconds * 2^(n-1)`。

5. **租约到期和回收边界**
   - 精确推进到 `expires`，验证旧令牌确认返回 409。
   - 分别测试“由下一次 claim 触发回收”和“由 `/sweep` 触发回收”。
   - 测试回收晚于 `expires + backoff` 时，新尝试可立即领取。
   - 构造超过 100 个同时到期尝试，验证 claim 的本组 100 条上限和 `/sweep` 的有界分页；必要时循环 sweep 到 `recovered=[]`。

6. **僵尸属主与栅栏测试（最关键）**
   - A 领取后暂停 A 的处理线程或注入长延迟，使其超过租约和退避。
   - 让 B 领取尝试 2。
   - 恢复 A，让 A 继续执行旧的下游写入并尝试确认 Quaybell。
   - 断言：
     - A 对 Quaybell 的提交得到 409；
     - A 携带旧 `(delivery_id, attempt)` 栅栏的下游写入被拒绝；
     - 或相同业务幂等键的第二次提交没有产生第二份副作用；
     - 最终下游状态等价于只有 B 的一次有效提交。
   - 该测试中允许观察到两个处理执行在时间上重叠，因为这是真实的僵尸窗口；门禁应判定“旧代际不能提交效果”，而不是错误地假设语言线程会被 Broker 杀死。

7. **重平衡/发布演练**
   - 在持续热键和低频键流量下滚动重启消费者。
   - 随机发送 `SIGTERM`、`SIGKILL`，注入 HTTP 503/超时和 SQLite busy。
   - 验证热键接管时间、冷键等待时间、409 数量、过期尝试数量和死信数量符合预期。
   - 对同一键的下游变更记录按栅栏排序，确认没有较旧代际覆盖较新代际。

8. **生产影子或流量回放**
   - 用脱敏生产消息或镜像流量在预发跑峰值 2 倍。
   - 接入真实下游的预发实例，验证幂等表/栅栏表和唯一约束。
   - 看板至少包含：各 `cause` 的数量和最老年龄、领取速率、处理并发、租约到期、重试、409 旧令牌、DLQ、每 `lane` 活跃处理数、下游栅栏拒绝/幂等命中。

上线签收条件应明确为：

- 并发测试中同 `lane` 的有效处理计数从未超过 1；
- SQL 不变量零违规；
- 所有僵尸/超时场景后，下游没有重复或旧覆盖新的有效副作用；
- 热键演练时冷键端到端等待低于约定 SLO；
- 回滚和旧积压收尾负责人已在岗。

## 6. 旧积压由谁收尾

### 6.1 拆分新组时

新消费组只对“建组之后发布且标签匹配”的消息创建投递。已有消息在发布时已经固定了 fanout 集合，后建组不会追认；重复发布同一生产键也只会返回第一次的 fanout 回执，不会补投新组。

因此：

- **拆分前的旧积压由原消费组的负责服务/团队收尾。**
- 新热键组、新低频组的负责人只负责切换点之后进入这些组的新投递，除非另有书面迁移交接。
- Quaybell 当前没有把等待中投递跨组移动的接口。`redrive` 只处理死信，而且仍是在原组、原 `lane` 追加后继。
- 如果业务要求新热键团队接手旧热键积压，只能显式选择：
  1. 在切换前由原团队清空旧组；
  2. 原团队继续运行 drain 工作池，直到旧积压清零；
  3. 或编写一次性迁移/重发程序，把旧消息作为新消息发到新组/新频道，并使用业务幂等键防止重复副作用。

还要注意：如果原组使用空标签 `{}`，它会匹配所有新消息。在同频道直接新增热/冷标签组后，切换后的新消息会同时进入原组和新组。若原 drain 池继续全量处理，会形成预期内的双消费；必须依靠幂等，或让 drain 版本按切换高水位识别新 fanout 副本并安全跳过/确认。更干净的方式是：

- 先让生产者给消息加路由代际标签，使旧组不再匹配新流量；或
- 生产者切换到新频道，旧频道和旧组只做积压排空与证据保留。

当前没有删除消费组或修改订阅标签的接口；即使所有消费者下线，订阅仍会为匹配的新消息创建投递。因此退役旧组必须先切断生产路由，而不是只停进程。

### 6.2 同组调整固定归属时

投递仍在同一个组和 `lane` 中，不需要迁移持久记录，但要明确责任：

- **旧属主**：收到重平衡信号后，只负责已经持有的尝试，在租约内 `ack` 或到期前 `nack`；不得继续领取新批次。
- **最终键属主**：按稳定哈希/分片映射，负责该 `lane` 上尚未领取和后续重试的积压。
- **滚动发布负责人/值班 DRI**：负责观察看板，确认所有 `lane` 没有长期 `leased/expired/blocked`，并决定是否执行 `/sweep`。
- **死信负责人**：负责失败原因、业务修复和 `/redrive`；重投子投递在队尾，需要继续观察到终态。

积压收尾完成的定义不只是“消费者进程已升级”，而是：

```text
该旧组 waiting = 0 且 leased = 0；
所有 dead 已完成业务处置、重投并 ack，或被负责人明确接受/归档；
相关消息的证据/审计已保留；
旧订阅不再接收新流量，或已进入明确的退役保留状态。
```

保留策略不能代替收尾：只要消息还有 `waiting` 或 `leased` 投递，保留清理就不会删除它；但 `dead` 属于终态，可能在业务尚未复查时达到保留期并成为清理候选。因此死信必须在保留窗口前有人工处置结论。

旧投递沿用发布时的策略版本，所以排空 ETA 要按旧的租约和指数退避计算；只有死信重投产生的新投递才使用当前策略。

## 7. 建议落地顺序

1. 用频道看板导出当前热键、冷键的 `lane`、`cause`、队首和年龄，确认问题是顺序阻挡、消费容量还是本地串行。
2. 修正过粗的 `lane`：不同业务实体必须使用不同顺序键。
3. 先在同一组内实现有界的 `lane` 串行 actor 和跨 `lane` 并发，消除“一个批量串行处理所有键”的问题。
4. 为处理链路补 `(delivery_id, attempt)` 栅栏和 `(channel, group, message_id)` 幂等表。
5. 把确认、重试、过期、僵尸属主和并发领取测试加入上线门禁。
6. 选一个最持续的热键做金丝雀：生产者加热标签，建专用组和工作池，用 `/preview` 验证路由。
7. 明确旧组 drain DRI 和完成标准；优先采用“旧路由/旧频道排空，新标签组/新频道接新流量”的切换。
8. 低频键保持共享组；只有本地状态归属成为硬需求时，再引入虚拟分片标签组，或为 Quaybell 增加服务端键归属/过滤领取能力。
